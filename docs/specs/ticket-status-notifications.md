# Spec: Ticket Status Notifications

> Status: **Approved** 2026-10-19 (ADR-008 accepted).

## Objective

Start the notification work for issues #9 and #8. A signed-in user who created a ticket sees a
notification pane in the site header that shows when a technician changes that ticket's status.
Polling keeps the pane current without a page reload.

ADR-007 added the technician status-update endpoint and UI. This slice adds notifications to that
endpoint and stops technicians at `RESOLVED`.

## Assumptions

1. Only tickets with a stored `creatorUserId` have an owner who can be notified. Tickets submitted
   without signing in have no recipient.
2. Tickets posted with `postAnonymously` still notify their creator. The notification is visible
   only to that creator, so the public anonymity from ADR-005 is preserved.
3. "Constant updates" (#9) is met by polling every 30 seconds and when the window regains focus.
   Server-sent events and WebSockets are deferred.
4. Notifications are stored in PostgreSQL with a read state. They are not delivered by email or
   push.

## Contract

### Status update (technician)

- `PATCH /api/tickets/:ticketId/status` accepts `{ "status": TicketStatus }` and returns the
  updated ticket.
- It returns `401` without a valid session, `403` for non-technicians, `404` for an unknown ticket,
  and `400 INVALID_STATUS_TRANSITION` for a skipped, backward, or `COMPLETED` change.
- Transitions advance one adjacent stage along `OPEN → UNDER_REVIEW → IN_PROGRESS → RESOLVED`. A
  status change updates `updatedAt`. A same-status request returns the unchanged ticket and creates
  no notification.
- `RESOLVED → COMPLETED` is reserved for the ticket owner's confirmation or an automatic
  completion after a set period (issue #8, follow-up slice). Technicians cannot set `COMPLETED`.
- The status update and its notification are written in one database transaction.

### Notifications (ticket owner)

- `GET /api/notifications` requires a session. It returns
  `{ notifications: Notification[], unreadCount: number }` with the caller's 20 newest
  notifications.
- `Notification` is
  `{ id, ticketId, ticketTitle, previousStatus, newStatus, createdAt, readAt | null }`.
- `POST /api/notifications/read` requires a session and marks all of the caller's unread
  notifications as read. It returns `204`.
- A user can never read or modify another user's notifications. The recipient is resolved
  only from the session.
- No notification is created when the actor is also the ticket's creator.

### Persistence

New `notifications` table:

| Column            | Type            | Notes               |
| ----------------- | --------------- | ------------------- |
| `id`              | uuid PK         |                     |
| `user_id`         | uuid FK users   | `on delete cascade` |
| `ticket_id`       | uuid FK         | `on delete cascade` |
| `previous_status` | `ticket_status` |                     |
| `new_status`      | `ticket_status` |                     |
| `created_at`      | timestamptz     | default now         |
| `read_at`         | timestamptz     | nullable            |

Index: `(user_id, created_at desc)`. The migration is generated by Drizzle and is additive.

### UI

- A notification button sits in the header next to `AccountMenu` for authenticated users only.
  It shows an unread-count badge, and its label includes the count.
- Opening the button shows a pane with notifications such as “_Printer offline_ moved from Under
  review to In progress”, a timestamp, and a link to the ticket. Opening the pane marks
  all notifications read.
- The pane has an empty state, a non-blocking error state, and keyboard and Escape handling that
  match `AccountMenu`.
- The browser polls every 30 seconds and when the window regains focus.

## Tech Stack and Structure

- `apps/api/src/database/schema.ts`: `notifications` table and generated migration in `apps/api/drizzle`.
- `apps/api/src/tickets`: status contract, route, and repository method (transactional notify).
- `apps/api/src/notifications`: contract, route, and repository interface. The Postgres
  implementation goes in `apps/api/src/database`.
- `apps/web/src/notifications`: `notification-api.ts` and `NotificationPane.tsx`, mounted in `App.tsx`.

## Testing Strategy

- Route tests: status update auth (`401`/`403`), `404`, adjacent/backward/skip/same-status transitions, and the
  technician ban on `COMPLETED`. Notification list and mark-read auth, plus isolation between users.
- PostgreSQL integration tests: the status change and the notification are written
  together. Nothing is created for unowned tickets or when the owner is the actor. Cascades work
  on user and ticket delete.
- Component tests: the badge count, the pane listing, empty and error states, mark-read on open,
  polling using fake timers, and the pane hidden for anonymous visitors.

## Boundaries

- Always: resolve identity and role from the server session, scope every notification query by
  session user, keep React escaping, and version schema changes.
- Ask first: email or push delivery, SSE or WebSockets, notifications for replies or assignment,
  and status history beyond the notification rows.
- Never: expose a creator's identity on anonymous tickets, allow anonymous status changes, or
  accept a client-supplied recipient or actor.

## Success Criteria

- A technician can advance a ticket's status up to `RESOLVED` through the API. Invalid
  transitions are rejected.
- The signed-in creator of that ticket sees an unread badge within one poll interval and can read
  the change in the header pane.
- Other users, anonymous visitors, and unsigned ticket submitters see no notification.
- All quality, migration, coverage, build, and smoke checks pass.

## Deferred to the Issue #8 Slice

- The ticket owner confirms `RESOLVED → COMPLETED`.
- A `RESOLVED` ticket auto-completes after a set period if the owner has not confirmed it. The
  period length, and whether it is configurable, is still to be decided.
- Both completions should create a notification through the same path as this slice.
- The technician status UI (separate change by another team member) should call
  `PATCH /api/tickets/:ticketId/status`.
